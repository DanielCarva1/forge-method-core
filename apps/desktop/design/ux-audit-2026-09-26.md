## Findings before changes

| Journey | Observed behavior | User impact | Correction |
| --- | --- | --- | --- |
| First launch | Home leads with **Continuar um projeto** and three explanation cards; there is no direct, obvious start-new route. | A newcomer must infer that Explore then Minha conversa is the creation path. | Make discovery/creation the primary action; make returning to a project secondary. |
| Select an idea | An illustrated theme carries an editable draft to Minha conversa, but that screen immediately presents folder and Codex controls. | A clear creative promise turns into unexplained setup; Send is disabled. | Explain the two prerequisites in plain language at the point of action. |
| Choose a new folder | The picker immediately submits **Conferir projeto**, which expects an existing Forge link. | A valid new folder produces an error before the person can choose **Iniciar projeto**. | Picker only selects; user explicitly chooses start or reopen. |
| Workspace | Three folder actions, connection controls, technical safety text and the last record are all exposed before a first message. | The real first step is buried; visual hierarchy diverges from the approved chat-led board. | Make setup steps prominent, move secondary details behind disclosure, keep conversation visually dominant. |
| Navigation and visual language | Five top-level links, a prominent appearance disclosure, a mostly text-only home hero and generic rectangular cards. Explore reuses the approved art but lacks the board's expressive framing. | The app feels more like a settings dashboard than a welcoming creative tool. | Simplify hierarchy and use the approved palette/art with restrained editorial styling; retain actual, not invented, project data. |
| My Projects | Empty-state explanation exists; the captured populated screenshot contains a mocked project, not a native one. | Cannot cite that screenshot as evidence of native project rendering. | Keep the list as local shortcuts; improve first-visit copy and test the native empty state separately. |

## Invariants and limits

No new project registry, generated progress, fictional preview, backend change or publication. Choosing a folder must not create files. Starting a project remains an explicit action through `start_project`; opening one remains read-only validation through `inspect_project`. A message remains unsendable until authenticated Codex connection. Visual comparison is to the original boards in `references/`, not a claim of pixel-identical implementation.

## Implemented and checked

- Home now leads with discovery rather than a return-only route. The workspace uses two plain-language steps, gives the conversation more space, and moves record/technical explanation behind disclosures. The approved palette and existing art remain; no fictional preview or progress was added.
- The folder picker no longer submits an existing-project lookup automatically. It only fills the path and names the two explicit next actions. The browser check asserts zero inspection calls immediately after selection.
- Browser UI checks **PASS** for navigation, theme/contrast, keyboard, narrow layout, project shortcuts, record state and conversation controls. Before/after visual captures were inspected. These checks use mocked native calls.
- A fresh debug build in `C:\ForgeFast\forge-desktop-ui-audit-target\debug\forge-desktop.exe` passed hidden-desktop native smoke: existing project readback, read-only rejection of an unlinked folder, explicit new-project initialization, authenticated Codex connection, enabled Send and appearance persistence. No message was sent. The updated native screenshot is `D:\Temp\User\forge-native-after-20260926.png`; the test switched to dark mode before capturing it.
- **NOT_RUN:** native Windows folder dialog selection after this change; actual model reply delivery; published installer or update. The browser picker test is not a substitute for the native dialog. The previously installed application is not this debug build.

## Remaining design work

The result is a deliberate first-pass correction, not a complete rendition of the approved conversation board. The board's preview and stage examples cannot be copied without real backend data. The home and workspace can still gain more of the approved botanical character and less setup-first friction, but those changes should be judged through further first-time user trials rather than invented screen content.

## Current journey coverage review — 2026-09-27

This review compares the current source UI with the approved boards in
`references/` and the accepted UI stories #87–#93. It does not mark those
issues complete; each has broader acceptance criteria. The source after public
0.1.14 is not yet a published update.

| Journey | Current evidence | Remaining boundary |
| --- | --- | --- |
| Welcome and discover an idea | Home and eight illustrated Explore categories use the approved art; the selected idea reaches an editable conversation draft. Browser navigation and layout passed. | The artwork supplies direction, not fictitious project data. |
| Find or start a project | Local shortcuts show name and full path; native project resolution and onboarding passed. | The shortcut list is device-local, not a complete project registry. A first-time visitor to an empty list previously saw only an “open” action. |
| Converse and return | Real Codex send/reply, same-conversation change, ordered restart history and the signed-out challenge/cancel were proven in the 0.1.14 package. | Genuine first-account browser authorization and default-browser opening remain NOT_RUN. |
| Review a result | Real local HTML/text/image preview, file-origin disclosure, change draft and protected content path passed focused/native tests. | A local static preview is not an interactive site or proof of publication. |
| See Forge direction | The read-only Forge record and accepted-objective revision history are visible in plain language. | Full historical decision semantics and a fresh Forge record for every Codex response are not established. |

The highest-impact *screen-state* gap within this UI review was the empty My
Projects route: it assumed an existing project, despite being a likely first
stop for a new user. The empty card now offers **Explorar ideias** and explains
that a folder may be empty or pre-existing; its other path is **Escolher uma
pasta** in the heading. Once a shortcut exists, that heading says **Abrir outro
projeto**. No project is fabricated, and the existing native resolution and
local shortcut mechanism are unchanged. The browser suite checked both routes,
the dynamic label, revalidation and narrow layout. A hidden native WebView
smoke passed after the source build; it exercised real Forge project onboarding
but did not use a fresh Windows account or send a new real Codex turn in this
slice. Visual capture: `C:/ForgeFast/forge-projects-empty-final.png` (browser,
controlled frontend, not native IPC).

The same first-use review found that **Continuar nesta pasta** looked actionable
with no folder selected, while the browser's native `required` bubble owned the
feedback and could leave the app status unchanged. The project form now keeps
the field semantically required but gives its own visible, live instruction,
focuses the path and marks it invalid when empty or whitespace-only. Editing or
choosing a folder clears the invalid marker. No empty path reaches Forge. The
browser suite and hidden native WebView both exercised this state; the latter
then canceled and selected a real Windows folder and continued onboarding.

## Real first-use agent/runtime alignment — 2026-09-27

A bounded real Codex turn on a disposable Forge-linked project exposed an
integration gap: the app read the project with pinned `forge-core 0.13.2`,
but the agent's shell resolved machine-wide `forge-core 0.12.1`. Requesting
the installed Start Forge skill did not make the executable match the app's
runtime. The original turn did read the skill, run `start` and `workflow
resume`, and ask a relevant product question, but with the older core.

Current source starts project-bound Codex subprocesses with the same resolved
Forge executable directory first on that subprocess's `PATH` and exposes its
absolute path as `FORGE_CORE_EXE`. The login-only subprocess is unchanged;
global PATH and Forge authority are not replaced. A second hidden native turn
confirmed that the agent resolved and invoked `forge-core 0.13.2`, ran
successful `start` and `workflow resume` against the selected disposable
project, read discovery guidance and asked who the recipe site's first version
should serve. It did not create the site or claim the user accepted an option.
The final answer, rather than an earlier progress message, was read from the
conversation; WebView reload restored it.

One trace limit remains: the agent attempted the `decision_required` variant
of `workflow intent accept-cooperative`, but its shell tool rejected the
composed command under host policy before execution. That variant is read-only
and should return a typed Decision Request without a ledger write; it was
incorrect to expect a durable pending-decision write at this stage. The agent
asked the question in chat, but the typed runtime return remains unverified.
That is not proof the Forge command itself rejected it.
The Start Forge skill is still supplied by the host installation rather than
the app bundle; clean-machine availability remains separate work.
